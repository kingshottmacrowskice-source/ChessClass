# 直播模块完整流程图

依据：2026-10-29 工作区现有代码。本文描述已实现行为，不是未来设计；按业务总览、接入、投票、走棋、互动、展示和生命周期分层。

## 1. 整体业务闭环

```mermaid
flowchart TD
    A[打开直播设置页] --> B[设置房间、连接开关、棋力、人设、模型、语音、画面]
    B --> C[配置保存到本机服务]
    C --> D[直播页或 OBS 浏览器源读取配置]
    D --> E[初始化标准棋局：观众白方，大肥鱼黑方]
    E --> F[接收 B站弹幕或本地测试消息]
    F --> G{消息类型与当前状态}
    G -->|白方回合的合法走法| H[按观众身份计票]
    G -->|白方回合 AI 确认投降意图| H
    G -->|其他消息| J[写入事件流，等待独立AI定时读取]
    H --> K[共用一轮：走法领先等10秒，投降领先等60秒；加票给原领先项不续时]
    K --> L[截止后选出票数最高走法]
    L -->|走法胜出| M[白方落子、动画、事件反馈]
    L -->|投降胜出| E
    M --> N{棋局结束?}
    N -->|否| O[Stockfish 分析，按棋力选黑方走法]
    O --> P[角色思考、吃子、搬棋、落子]
    P --> Q[黑方落子、特效、写入事件流]
    Q --> R{棋局结束?}
    R -->|否| F
    N -->|是| S[结局反馈]
    R -->|是| S
    S --> T{将死?}
    T -->|是| U[终结动画，30秒后自动重开]
    T -->|和棋| V[停留在结束状态，等待手动重开]
    U --> E
    V -->|新的一局| E
    J -.并行展示.-> F
```

**职责划分：** chess.js 判定合法走法和终局；Stockfish 19 负责黑方决策和分析；DeepSeek 负责自然语言走法识别和基于事件流的定时聊天。关闭 AI 开关后，明确走法投票与黑方引擎走棋仍然可用。页面底部虽然写着“DEEPSEEK PLAYS BLACK”，实际下棋决策由 Stockfish 完成。

## 2. 页面入口、配置同步与运行边界

```mermaid
flowchart TD
    A[应用入口 main.tsx] --> B{访问入口}
    B -->|#live 或 /live| C[LiveMode 直播画面]
    B -->|#live-settings 或 /live-settings| D[LiveSettings 设置页]
    B -->|#actions| E[动作预览页]
    B -->|其他| F[棋局分析页面]
    F -->|直播对练按钮| C
    C -->|返回分析| F
    C -->|新窗口打开设置| D
    D --> G[启动时读浏览器缓存]
    C --> G
    G --> H[请求本机直播设置]
    H --> I{服务端已有设置?}
    I -->|是| J[合并服务配置与尚未提交的本地修改]
    I -->|否，设置页| K[把旧浏览器配置排入保存队列]
    I -->|否，直播页| L[提示先到设置页保存]
    D -->|修改控件| M[立即更新画面和浏览器缓存，累计待保存字段]
    M --> N[PATCH /api/live/settings]
    K --> N
    N --> O[校验字段类型，串行合并，临时文件改名保存]
    O --> P[(data/live-settings.json)]
    P --> H
    J --> Q[直播画面采用新设置]
    Q --> R[本次请求结束后等待1秒]
    L --> R
    R --> H
    H -->|失败或5秒超时| S[保留待保存字段，显示重试状态]
    N -->|失败| S
    S --> R
```

- 设置页与直播源通过本机服务同步，不要求共享浏览器存储；OBS 新建浏览器源不会用自己的默认值覆盖服务设置。
- 默认值包括：自动连接开启、AI 关闭、深度 2、棋力 100、语音关闭。房间为空时不会连接。
- 直播展示模式、文字比例、棋盘角度影响呈现；投票、决策和对局状态仍由直播页面实例维护。
- **共享的是设置与弹幕服务，不是同一盘棋。** 每个 LiveMode 实例各自创建 Chess、VoteRound 和聊天记忆；同时打开多个直播页会各自运行。
- 配置和服务 API 由 Vite 插件在开发/预览服务中提供；单独复制静态页面不能替代这些服务。

## 3. B站扫码登录

```mermaid
flowchart TD
    A[设置页读取本机登录配置状态] --> B[用户点击扫码登录]
    B --> C{距离上次生成至少10秒?}
    C -->|否| D[提示稍后重试]
    C -->|是| E[取消旧会话，创建180秒有效的新会话]
    E --> F[服务端请求 B站二维码]
    F -->|失败| G[显示错误，用户刷新二维码]
    F -->|成功| H[浏览器显示二维码]
    H --> I[约每2秒轮询登录状态]
    I --> J{B站返回状态}
    J -->|等待扫码| I
    J -->|已扫码| K[提示手机确认]
    K --> I
    J -->|确认成功| L[服务端提取并校验必要 Cookie]
    L --> M[写入 server/bilibili.local.json]
    M --> N[页面显示已保存登录]
    N --> O[下次弹幕轮询发现 Cookie 改变]
    O --> P[关闭旧弹幕连接，用新凭据重建]
    J -->|过期、异常或超过轮询限制| G
    H -->|用户取消或离开设置页| Q[取消扫码会话]
    N -->|清除本机登录| R[取消未完成扫码，保存空 Cookie]
    R --> O
```

登录凭据保存在本机服务文件，页面得到的是状态和二维码信息。未配置 Cookie 时，弹幕服务仍会尝试匿名连接；能否获得有效观众身份取决于 B站返回数据。界面的“已保存登录”表示本机存在配置，并不等同于实时验证登录仍有效。

## 4. 弹幕连接、重连与去重

```mermaid
flowchart TD
    A{自动连接开启且房间为1至15位数字?} -->|否| B[不启动前端轮询]
    A -->|是| C[GET /api/live/bilibili?room=房间号]
    C --> D[本机中继读取 Cookie]
    D --> E{该房间已有连接且凭据未变?}
    E -->|是| K[返回连接状态与最近300条直播事件]
    E -->|否| F[创建或重建房间连接]
    F --> G[查询真实房间号]
    G --> H[获取弹幕服务器和认证 token]
    H --> I[建立 WebSocket，发送认证包]
    I --> J{认证成功?}
    J -->|是| K
    J -->|否或15秒连接超时| R[断开并安排自动重连]
    I -->|网络错误或连接关闭| R
    R --> S[退避等待3、6、9秒，最高30秒]
    S --> G
    J -->|成功后| T[立即发心跳，此后每30秒发送]
    T -->|检测距最后心跳响应超过65秒| R
    T --> U[解包，支持 zlib 和 Brotli 压缩]
    U --> V{是否有效弹幕或支持的互动通知?}
    V -->|否| W[忽略该事件或更新状态提示]
    V -->|是| X[规范化事件，生成会话加序号ID，保留最近300条]
    X --> K
    K --> Y{前端首次成功取得快照?}
    Y -->|是| Z[登记消息ID并作为历史事件存入，不计票或当作新互动]
    Y -->|否| AA[仅将未见过的消息交给 ingest]
    Z --> AB[请求结束后等1秒再拉取]
    AA --> AB
    C -->|请求失败| AC[显示错误，继续下一次轮询]
    AC --> AB
    AB --> C
```

- 前端去重集合超过 1000 条时保留最近 300 个 ID；服务端每条弹幕最多保留 300 字符、昵称最多 40 字符。
- 中继最多保存 8 个房间；满额时淘汰最久未使用的房间。每 15 秒清理一次，超过 60 秒无人读取的房间会断开。
- 用户点击断开后，前端停止读取；服务端房间连接通常由上述空闲清理回收，并非点击即立即关闭。
- 这是“服务端 WebSocket 接收 + 前端 HTTP 轮询快照”，高流量超过缓冲容量时可能漏消息。

## 5. 单条弹幕的分流与 AI 走法识别

```mermaid
flowchart TD
    A[B站新消息或本地测试消息] --> B[唤醒角色，更新最近互动时间]
    B --> C{对局已结束?}
    C -->|是| D[反馈：对局已结束]
    C -->|否| G{白方回合且不忙?}
    G -->|否| H[提示下轮白方回合再投票]
    G -->|是| E{AI 确认支持投降?}
    E -->|是| K[进入统一计票校验]
    E -->|否| I[本地匹配合法走法]
    I --> J{唯一明确匹配?}
    J -->|是| K
    J -->|否| L{AI 开启?}
    L -->|否| M[未计票：闲聊或走法不明确]
    L -->|是| N[进入识别队列，最多30条]
    N -->|队列已满| O[淘汰最旧消息，提示用明确走法重发]
    N --> P[每1.5秒检查，单次最多取12条]
    P --> Q{仍为白方回合、不忙且无识别在途?}
    Q -->|否| P
    Q -->|是| R[发送合法走法列表和弹幕给 DeepSeek]
    R --> S{返回时会话、棋局和开关仍有效?}
    S -->|否| T[丢弃过时结果]
    S -->|是| U[解析 JSON 数组，匹配原消息ID]
    U --> V[对模型走法再次做本地合法性校验]
    V -->|有效| K
    V -->|无效或未识别| M
    R -->|请求失败或格式错误| W[反馈识别失败，可用 e2e4 重发]
    K --> X[记录计票结果]
    D --> Y[事件流、飘屏和消息日志]
    H --> Y
    M --> Y
    N -.消息入队时即记录.-> Y
    X --> Y
```

本地支持 `e2e4`（UCI）、`e4` / `Nf3`（SAN）、`e2到e4` / `e2-e4`、`马到f3`，以及前缀“投票”。必须匹配当前合法着法，歧义不会直接计票。升变可用 `e7e8q` 明确指定棋子。

事件流与投票是并行用途：一条消息未计票，不代表它不能进入定时聊天上下文。黑方回合收到的走法不会自动保存到下一轮重新投票。弹幕现场保留最近 80 条，界面展示最近 12 条；飘屏保留至多 14 条、分 4 条轨道，减少动态效果模式下不显示飘屏。

## 6. 投票窗口与白方落子

```mermaid
flowchart TD
    A[收到合法走法或投降选项] --> B{观众ID为空?}
    B -->|是| C[拒绝：缺少观众ID]
    B -->|否| D{本轮该观众已投票?}
    D -->|是| E[拒绝重复票，不能改票]
    D -->|否| F{已到截止时间?}
    F -->|是| G[拒绝：本轮已截止]
    F -->|否| H[记录投票前领先项，再记录 用户ID 到 选项]
    H --> I{本轮第一票?}
    I -->|是| J[记录首票时间 first]
    I -->|否| K[若投给原领先项不续时，否则更新倒计时起点]
    J --> K
    K --> L[截止 = min 首票后5分钟，倒计时起点加当前领先项等待时长]
    L --> M[更新棋盘票数、加一特效、领先变化反馈]
    M --> N[每200毫秒检查结算条件]
    N --> O{白方、未结束、不忙、无棋盘运镜?}
    O -->|否| N
    O -->|是| P{已到截止且存在票?}
    P -->|否| N
    P -->|是| Q[按票数降序取第一项]
    Q -->|走法胜出| R[清空本轮票与待识别队列，锁定落子]
    Q -->|投降胜出| Y[重开标准棋局，清空本轮所有票]
    R --> S[chess.js 执行白方走法]
    S --> T[同步棋盘、反馈和480毫秒位移动画]
    T --> U{棋局结束?}
    U -->|是| V[终局流程]
    U -->|否| W[启动黑方引擎回合]
    W --> X[黑方落子后重新等待第一票]
```

- 没有首票时截止时间为无穷，不会自动替观众走棋。
- 首票启动倒计时。有效新票投给投票前领先选项时不重置；投给其他选项时重置。重复票和无效消息不续时。当前领先项为走法时等待10秒，为投降时等待60秒；领先项变化后按新领先项的时长计算。
- 平票没有随机或加赛逻辑：按稳定排序和 Map 插入顺序，先被投到的走法优先。
- 同一观众每个白方回合只能在普通走法与投降中选一项，共用用户票集合，不能重复投票或改票。投降不绘制棋盘箭头；若投降领先，其他走法不显示领先标记。
- 运镜可能推迟实际落子时刻，但不会延长已确定的投票截止时间。

## 7. 黑方引擎决策与角色动作

魔鱼模式开启时，改用本地游戏 AI，不调用 SF。当前支持普通走棋、破坏与临时皇后／马移动；规则、搜索、回退及历史段边界见 [魔鱼模式](demon-fish.md)。以下流程描述普通走棋分支。

```mermaid
flowchart TD
    A[runEnemy] --> B{黑方回合且未结束?}
    B -->|否| Z[返回]
    B -->|是| C[锁定回合，停止闲逛，显示思考]
    C --> D[用当前完整局面 FEN 构造分析请求，不重放历史棋步]
    D --> E{内存或持久化缓存命中且有效?}
    E -->|是| H[取得 bestmove 和候选变化]
    E -->|否| F[初始化浏览器 Stockfish Worker]
    F --> G[按设置深度搜索，最多5条候选]
    G --> H
    H --> I{棋力为100?}
    I -->|是| J[采用最优走法]
    I -->|否| K[按棋力概率选择最优、次优或随机合法走法]
    K --> L{所选走法已有候选分析?}
    L -->|是| M[把对应候选调整到第一项]
    L -->|否| N[限制根走法，再分析该选择]
    J --> O[补足角色思考节奏，预演走法和吃子位置]
    M --> O
    N --> O
    O --> P[把引擎分析写入事件流]
    P --> Q[等待当前棋盘运镜结束]
    Q --> R[注视目标格，显示瞄准和表情]
    R --> S{吃子且攻击方式不是冲撞?}
    S -->|是| T[走到攻击位置，踢击或射击被吃棋子]
    S -->|否| U[走到己方棋子旁]
    T --> U
    U --> V[隐藏原棋子，抬起并搬运]
    V --> W[走到投掷位置，抛下棋子并显示落地特效]
    W --> X[如为冲撞吃子，在此击飞目标]
    X --> Y[提交黑方真实走法，执行 afterMove]
    Y --> AA[等待480毫秒，落子事件供AI后续定时读取]
    AA --> AB[解除忙碌，等待观众或进入终局]
    F -->|失败| AC[恢复角色显示，报告引擎或动画失败]
    G -->|失败| AC
    N -->|失败| AC
    V -->|失败| AC
    W -->|失败| AC
    AC --> AD[黑方且不忙时显示重试引擎走棋按钮]
    AD --> A
```

引擎默认搜索参数为单线程、16 MB Hash、最长搜索时间参数 12 秒；直播调用同时指定深度，实际结束受引擎搜索条件影响。Worker 需要跨源隔离及 SharedArrayBuffer，Vite 配置提供 COOP/COEP 响应头。

动作过程会检查会话代数和页面存活状态；重开后旧动画不能继续提交旧局走法。吃过路兵时，目标被吃棋子位置使用原所在行计算。棋子位移动画另处理王车易位的车。

## 8. 独立 AI 聊天与定时事件流

原先的棋后主动点评、弹幕停顿触发AI回复、欢迎与闲置聊天已从直播主流程移除；重开和唤醒可显示本地短句，并记录实际显示的话。棋盘只产出事件，由独立 AIChat 模块定时读取；投票用的自然语言走法识别仍独立保留。

```mermaid
flowchart TD
    A[弹幕、入场、礼物、投票、落子、分析、重开、角色发言] --> B[棋盘写入带序号和时间的事件流]
    C[独立 AIChat 启动] --> D[首次等待10秒]
    D --> E[按已确认游标区分history与newEvents，并读取当前局面]
    B -.只存储，不触发请求.-> E
    E --> F[根据新增事件数与读取间隔计算流速]
    F --> G[下次间隔 = 目标4条事件的等待时间，限制10秒至10分钟]
    G --> H{有新事件?}
    H -->|否| I[不请求模型，静默时等待时间翻倍]
    H -->|是| S{历史至少24条或超过6000字符?}
    S -->|是| T[AI压缩较早历史，保留最近8条原文；失败保留原历史]
    S -->|否| J[人设与规则提示词 + 历史摘要与近期历史 + 新事件 + 当前局面]
    T --> J
    J --> K[调用聊天模型，等待完整结果]
    K -->|成功且仍为本次会话| L[确认读取游标，返回完整回复给棋盘]
    L --> M[气泡、语音、日志和受控切歌]
    K -->|失败| N[保留未确认游标，下次定时重试]
    I --> O[等待下一次定时读取]
    M --> O
    N --> O
    O --> E
    P[重开、关闭AI、退出] --> Q[取消在途请求并使旧结果失效]
```

- 初始间隔为10秒；公式为 clamp(10000, 600000, 本次与上次读取相隔毫秒数 × 4 / 新增事件数)。没有新增事件时按上次实际间隔翻倍，直到10分钟。
- 一次最多一个聊天请求在途；完成后距下次读取至少10秒。请求耗时不会导致并发补发。超长请求期间不会强行启动下一次读取。
- 新事件不会主动唤醒模块或提前重排定时器；若当前已退避到10分钟，新消息等待下一个定时点才被读取。
- 事件包括 session、chat、vote、move、analysis、entry、follow、share、gift、guard、superchat、like、speech；每条含 id、at、kind、data。chat 记录原弹幕及处理反馈，vote 记录成功计票及排名，move 记录真实落子及新局面，analysis 记录引擎候选与可能变化。
- 事件流保留最近300条。溢出数量作为 droppedEvents 告知模型；成功后才确认游标，请求期间新来的事件留到下次。失败则下次重读尚未确认的事件。
- 无新事件不请求模型；模型可返回空文本表示没有值得说的话。完整回复再返回棋盘显示和可选播报，不逐字显示中间结果。
- 不再单独请求棋后解说。定时读取时，未压缩历史达到24条或序列化超过6000字符，可用解析模型压缩较早历史（600输出token），保留最近8条原文。摘要逐次合并，目标400字，存储上限1500字符；失败或空摘要保留原历史继续聊天，下个定时点可重试。重开会清空摘要并取消在途压缩。
- 请求字段明确区分 historySummary（更早历史摘要）、history（近期历史，最多40条）、newEvents（本次未处理事件）与 window（成功处理游标至当前读取边界）。压缩只处理历史，绝不把本次新事件提前并入摘要。最近5次AI回复另作去重参考。
- speech 标记 source=local 或 ai；只记录已显示的非空文字。仅有角色发言时推进游标但不请求模型，这些发言留作后续历史，避免AI回应自己。当前本地短句为重开及唤醒提示。旧的点评概率配置不再影响直播。
- 重开清空事件流与回复上下文，记录新局事件，并重新等待10秒；关闭AI或离开页面取消调度和在途聊天请求。

升变并同时将死时只播放将死终结，附带“升变 · 将死”信息。内置切入动画正常为 3.4 秒，减少动态效果模式下为 1.5 秒。视频来自 `public/live-videos/promotion` 与 `public/live-videos/checkmate`，支持 mp4、webm、ogv；未放视频仍可显示内置效果。

**只有棋盘运镜会明确阻塞白方结算和黑方搬棋阶段。** 普通视频/切入层不应理解为全局暂停棋局。减少动态效果模式会跳过或减少部分视觉表现，但仍保留业务流程。

语音失败通常被调用方吞掉，文字交互继续；没有实现远程语音失败后自动切换浏览器语音。BGM 播放失败会被忽略，浏览器自动播放限制可能导致开场没有声音。切歌请求必须经过播放器自身校验，模型输出标记不能绕过“已完整播放一次”的限制。

## 11. 投降、重开、退出与异常恢复

```mermaid
flowchart TD
    A[AI 根据语义确认明确支持本方投降] --> B{白方可投票且用户本轮未投任何选项?}
    B -->|否| C[拒绝或提示已投过]
    B -->|是| D[加入本轮统一投票，投降领先时等待60秒]
    D --> E[与走法共用每200毫秒结算检查]
    E --> F{截止且白方未终局、不忙、无运镜?}
    F -->|否| E
    F -->|是| I{统一最高票选项为投降?}
    I -->|否| J[执行胜出走法，清空整轮票]
    I -->|是| K[reset 重开]
    L[点击新的一局] --> K
    M[将死后30秒且仍为原局] --> K
    K --> N[epoch递增，取消模型请求、定时聊天和闲置动作]
    N --> O[清理特效、队列、票数、消息日志和事件流]
    O --> P[销毁旧引擎，新建引擎与标准棋局]
    P --> Q[恢复开场音乐、角色默认状态、白方等待首票]
    R[返回分析或页面卸载] --> S[标记页面失效、递增epoch、取消在途请求]
    S --> T[关闭本页轮询与计时器，销毁引擎，停止BGM与运镜]
```

现有实现的边界：

1. 投降与所有走法共同排名，共用一人一票与截止检查；平票时投降始终排在所有走法之后，走法之间按首次获票顺序。每次本轮结算清空所有票，不跨白方回合保留投降票。
2. 投降同样只在白方可投票时接收，并在白方空闲且没有棋盘运镜时结算。投降胜出通过 reset 重开，旧局异步工作通过 epoch 和取消请求失效。
3. 将死的双方都设置 30 秒重开；和棋分支没有自动重开定时器。
4. 重开清空事件流和独立AI最近回复上下文，新会话延迟10秒首次读取。
5. 重开保留设置与弹幕连接，不重新扫描历史弹幕。刷新页面则新建本页棋局，没有恢复上一盘完整状态的流程。
6. AI关闭会清空识别队列并屏蔽旧识别结果，同时停止定时聊天并中止在途聊天请求。
7. 退出和重开没有统一取消远程 TTS 音频播放的流程，不能把“取消所有异步工作”理解成已经覆盖全部音频。
8. 引擎或动画异常会显示错误并解除忙碌；黑方回合可手动重试，不会自动改为观众替黑方走棋。

### 直播互动协议与历史边界

服务端 roomEvents 是统一事件队列，messages 保留仅弹幕的兼容视图；前端优先使用 roomEvents，按同一消息ID去重。支持 INTERACT_WORD / INTERACT_WORD_V2 的入场、关注、分享，SEND_GIFT / SEND_GIFT_V2（含批次内每个礼物）、GUARD_BUY、SUPER_CHAT_MESSAGE 与 LIKE_INFO_V3_CLICK。COMBO_SEND 累计通知不重复算作新礼物；陌生或畸形通知忽略，不影响弹幕连接。礼物与醒目留言不会进入走法识别或计票。

初次连接获取的缓存标为 historical，仅作为历史上下文；新快照中首次出现的ID才进入 newEvents。正常事件在聊天成功后从新增区转为历史；失败保留新增区等待定时重试。历史与新增各保留原事件时间、类型和序号，角色本地短句和AI回复标注来源。缓冲区共保留最近300条，历史发送窗口最多40条，超出缓冲的未读数量以 droppedEvents 报告。

协议字段参照项目维护者的 [blivedm 消息模型](https://raw.githubusercontent.com/xfgryujk/blivedm/dev/blivedm/models/web.py) 和 [V2 protobuf 字段定义](https://raw.githubusercontent.com/xfgryujk/blivedm/dev/blivedm/models/pb.py)。此处验证采用模拟通知，不代表真实房间一定推送每类事件。
